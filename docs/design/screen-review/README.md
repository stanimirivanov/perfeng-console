# M05 screen information architecture — steps 1 and 2

**For design review.** [Open the standalone HTML gallery](index.html). All snapshots are labeled design fixtures. They have no scripts, provider calls, submission handlers, browser storage, framework code or package dependencies. Open locally. The historical gallery predates the confirmed layout. Implement Scenario Lab under Verification in the Console, with a distinct Material theme and text label for authorized maintainers.

## Navigation and release boundaries

1. **Primary entry (P):** CI acceptance supplies a safe canonical Run link → authenticate if needed → return to Run detail → inspect run-used baseline comparison → review a new rerun intent → read the authoritative receipt → open the real child on the same Run route. A copied link carries no authority. Exact lookup is an alternate entry. The child page in this packet illustrates a second instance of the same screen.
2. **Supporting operations:** Runs → create; active Run → cancellation review; comparison → exact baseline; Resources → catalog/baselines; Diagnostics → health/native coverage/gaps. General baseline transitions default off. Run discovery beyond exact lookup stays a gap.
3. **Post-pilot:** catalog → onboarding or policy proposal → reviewed Git PR → verified publication → eligible to launch. Draft, merged and published are UI workflow descriptions, never guessed provider lifecycle values.
4. **Optional verifier (V):** independently authorized maintainer entry → admitted scenarios → campaign findings and a single parameter-bound approval → ordinary Run detail for a real cluster Run. Synthetic Tier A has no Run ID. The product distribution can start with V absent.

## State contract used by all sketches

| Variant | Display rule |
|---|---|
| Example | Complete static layout. Existing schema fields, required future reads and unsupported sections are distinguished. |
| Empty | No input/intent yet, or a *validated* empty collection. Missing list/inventory endpoints display NOT OBSERVABLE, never a zero count. A scoped 404 is a concrete lookup outcome. |
| Loading | Clear affected previous values. Identify the operation in progress. Suppress dependent mutations. |
| Error | Preserve safe distinctions: forbidden, scoped not-found, invalid payload/digest, 409 revision/intent conflict, validation refusal. Do not echo an upstream secret, supplied URL or another team's identity. |
| Backend unavailable | Clear affected live provider data and disable dependent writes. Do not fall back to the example layout. An individual endpoint error affects its own data; a shared transport/session failure invalidates its generation. Static gap metadata survives. |
| UNKNOWN value | A missing optional measurement/identity or unproven outcome alongside valid observations. Show a reason. It is neither numerical zero nor a provider verdict. A lost mutation response requires reconciliation. |

The product BFF envelope (planned) carries status, observedAt, validUntil on CURRENT, provider/config generation, contract digest and source operation. CURRENT / UNAVAILABLE / NOT_OBSERVABLE / FORBIDDEN / NOT_FOUND / INCOMPATIBLE describe observation state. Loading/empty are presentation phases. Follow the plan's bounded polling, 3 s read deadline, ≤10 s validity and per-resource response fencing. Disable dispatch when any required source is unavailable. Separately authorized disposable recovery belongs exclusively to a healthy verifier adapter. Historical receipts may be opened explicitly, are dated, and never refill live values.

## Contract interpretation

- Execution, quality, SLO, regression and evaluator results use separate vocabularies. The 14 Run states and allowed next states come from the published transition map. Terminal states have no outgoing edges. Failure codes are VALIDATION_FAILED, INFRASTRUCTURE_ERROR, PIPELINE_TIMEOUT, TOOL_ERROR and ANALYSIS_ERROR. Only display the returned code/message; do not infer causation from a state name. [Run API][run] · [Transitions][edges]
- Baseline states are CANDIDATE, QUALIFIED, APPROVED and RETIRED. The lifecycle list is actual provider evidence. A baseline that is APPROVED today is not proof it was selected on the historical Run. [Run API][run] · [Baseline fixture][base]
- Research §27 defines the six **presentation sections**. The analysis schema defines **values**: quality PASS/INVALID/UNSTABLE/INCONCLUSIVE/NOT_EVALUATED; SLO and regression PASS/FAIL/INCONCLUSIVE/NOT_EVALUATED. Research’s six display classes are PASS/WARN/FAIL/UNSTABLE/INVALID/INCONCLUSIVE. WARN is not accepted by the current rule schema. Preserve NOT_EVALUATED. Overall and diagnostics stay UNKNOWN when absent. No implied significance. [Analysis schema][analysis] · [Rule fixture][rule] · [Policy fixture][policy]
- An integration publication may already carry data.native.runId, data.native.policy and nullable data.native.baseline plus the artifact identity. It requires authorized issuer/request scope. No general reverse mapping or authorization follows from a native Run ID. PR46–48 must bind the comparison for the CI entry. [Integration API][integration] · [Publication fixture][pub]
- PR49–51 supply lineage, current entitlement checks and durable audit semantics. An uncertain rerun is reconciled with its original key. Withdrawal/revocation refuses the rerun, never silently swaps a baseline. Baseline transitions require separately authorized actors and expectedRevision. [Plan](../../../tasks/plan.md)
- Native worker API operations serve workers. Hide capability/grant fields even in errors. The catalog is principal-scoped; require complete consistent pagination before enabling selections. Health readiness measures startup acquisition. [Native API][native] · [Catalog contract][catalog] · [Metrics handler][metrics]

## Judgment calls for review

1. Use Run detail as the CI landing and retain an exact-ID lookup for people without a link. No default run list, trend chart or dashboard until there is a scoped read.
2. Keep comparison within the Run journey but make the six-section report separately navigable. Present requirement and regression side by side conceptually; execution COMPLETED and a regression FAIL must both remain visible.
3. Give rerun review and receipt dedicated screens so the planned actor/lineage proof is unmistakable. Represent cancellation separately because it operates on the current Run. A child snapshot reuses the parent layout.
4. Keep baseline lookup and lifecycle together. Put artifact/provenance claims beside Run evidence. Static wireframes abbreviate long digests for scanning and label abbreviations; runtime must allow exact values to be inspected before review.
5. Prefer native tables and ordered lists at this fidelity. Treat the transition graph as permitted edges, not a diagram of recorded events. The example uses one observed revision and does not synthesize prior steps.
6. Keep post-pilot proposals visually separate from operational actions. Show only Git review → publication semantics; repo mapping, form fields and status wire formats await PR60–62.
7. Present Verification as a distinctly themed, labeled area inside the Console. Keep campaign expectation levels, approvals and findings together, without mixing synthetic rows into the product Runs collection.
8. Use one consistent fixture thread from the published search-browser example. Fixture commit labels, session ages, intent actors and prospective receipt values are illustration only. No performance numbers are product claims. Render the health and catalog examples at their imaginary observation time.
9. Use static fragment links for reviewer-selected states. All action buttons are disabled; “preview” links switch drawings only. A state fragment replaces the received content, including on direct navigation. Gap-only screens show a designed absence, not a fictional inventory.
10. Keep shell/UI state independent from Angular Material visuals here. Current deliverables stop at navigation, content hierarchy and state behavior. Material components, responsive final styling, keyboard/focus verification and WCAG 2.1 AA review await owner approval.
