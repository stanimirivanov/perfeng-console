# Console constraints

The browser operates through its same-origin BFF. Provider credentials stay server-side. The BFF can read protected configuration and call fixed authorized endpoints. The simulator runs separately. Only approved environment adapters may perturb disposable targets. The independent evaluator consumes immutable observations through declared contracts.

- Pin code generation and the complete local contract closure by digest. Admit external tools with exact versions, license and security review. Runtime schema fetching and arbitrary URL proxies violate the boundary.
- Freeze expectations, repetitions, input identity and tolerances before execution. Bind independent review to the exact manifest digest. Evaluate current-phase obligations and research targets separately. Preserve every mismatch as a FINDING.
- Preserve synthetic labels, abstentions, unknown values and declared denominators. Tier A has 600 active seconds and Tier B has 3600. Exclude only initial shared provisioning and quiescent approval waits. Count concurrent active work once.
- Require separate target-bound approval for each cluster mutation, including recovery. Journal intent before dispatch. An uncertain external effect blocks replay until reconciled. Keep residual work and partial evidence inspectable.
- Treat CP outage as unavailable for live platform observations. Dated receipts are explicitly historical. Each displayed product claim needs a scoped provider observation or a reason it is missing.
- Exercise all declared checks. Keep secrets outside source, fixtures, logs and browser outputs. Record incomplete work explicitly. Preserve previously approved expectations and receipts when findings are reviewed.

The [sensor inventory](HARNESS.md) distinguishes today's mechanical controls from acceptance obligations that need the product runtime. Require explicit human review to change these constraints.

## Approved requirements

The eleven requirements below retain the approved scenario constraints. The confirmed intent and current plan govern product delivery priority and the single Console. Implementation is authorized issue by issue.

1. **Expectations precede execution.** Freeze a versioned manifest containing scenario inputs, seeds, repetitions, source references, policy/contract pins, expected outcomes and tolerances before any run. Record its SHA-256 in every receipt. Derive expectations from research, contracts and policy semantics, never from observed platform output.
2. **Never move the target.** Do not edit expectations, thresholds, repetitions or classifications to match a campaign's results. A discovered specification error requires a separately reviewed new expectation version; preserve the original results and FINDING. Do not fix platform code within a characterization campaign to obtain green.
3. **No silenced checks.** No skipped/deleted assertions, suppression comments, swallowed errors, weakened validators or selective reporting to get green. Unavailable prerequisites and N/A cases are recorded with reasons, owners and gaps; they are not passes. No secrets in source, artifacts, browser payloads or logs.
4. **Review before execution.** Every expectation set requires an adversarial fresh-context review against its cited sources, reconciliation of substantive findings and an approval record bound to the manifest digest before a run. Offer a cross-model second opinion under the requested doubt-driven workflow. Unresolved ambiguity blocks the affected scenario, not unrelated approved cases.
5. **Independent oracle.** The simulator owns the evaluator. It does not import analysis verdict/comparison functions or copy observed outputs into expected values. Tier B observes Perfeng only through authorized public APIs; missing observability is an explicit gap, never permission to query private storage.
6. **Two expectation levels, both visible.** Evaluate current-phase obligations and research targets separately. A research limitation is not an exemption from a current contract. A known bug is a FINDING, never a normative current-phase expectation. Preserve unsupported targets as explicit unmet capabilities.
7. **Bounded campaigns.** Tier A: 10 minutes. Tier B: 60 minutes. Exclude initial shared-environment provisioning and quiescent human approval waits only; include scenario-specific preparation, baseline execution, active execution, observation, recovery and teardown. Waiting while external campaign work remains active or its state is uncertain does not pause the active clock. Declare repetition counts and stop policy before execution, using documented duration assumptions. Budget exhaustion records unexecuted cases and insufficient coverage; no adaptive reduction of the declared denominator.
8. **Explicit mutation approval.** Confirm each Tier B mutating step, including test submission, cancellation, baseline lifecycle operations, fault injection, restart and cleanup. Show target, exact operation, expected effects and recovery action. Never infer authorization for a later step. No automatic cleanup mutation without its explicit approval; report residual resources if approval is pending.
9. **Isolation and authority.** Fault injection is restricted to a dedicated disposable environment through environment-owned harnesses. Never edit Perfeng databases, manufacture lifecycle states, impersonate workers or mutate production. Browser and BFF have no Kubernetes, shell or storage authority.
10. **Truthful evidence.** Label synthetic Tier A evidence everywhere. Preserve raw observations, receipt timestamps, source versions and immutable campaign results. Never display historical campaign evidence as current health or as outage fallback. Every expected/actual mismatch is a FINDING; an inconclusive evaluation cannot be relabeled PASS.
11. **TDD for implementation.** Tests for simulator/evaluator/BFF/UI behavior precede implementation and demonstrate the relevant failure. Platform scenario findings and harness correctness tests are distinct: a correct harness may report platform failures. Implementation is authorized issue by issue; each live mutation requires its own approval.

## Product constraints

Maya's first journey is CI link → exact baseline comparison → attributable real rerun.
The Console contains a distinctly themed and text-labeled maintainer Verification area.
The optional runner has separate installation, credentials, execution and rollback.
An absent runner leaves ordinary Run operations usable and campaign actions disabled.
Service-scoped authorization applies to every read and write; baseline approval is a separate right.
Every upstream bearer stays in the BFF. The browser receives session-bound observations.
Configuration proposals flow through reviewed Git changes and exact published identities.
